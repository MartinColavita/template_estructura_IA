1.Qué es y para qué

Una sección integrada del repo que toma un pedido pobre (un título suelto, un link, un "ver adjunto") o una ficha de documentación y devuelve un work item profesional de Azure DevOps (Épica, Feature, Historia, Tarea o Bug), completo y trazable. El método es agnóstico de dominio: el dominio concreto lo aporta el Cerebro Digital del proyecto (cerebro-digital/), que es la fuente de solo lectura.

Qué se puede hacer con él: redactar un ticket suelto, mejorar una tarjeta existente, bajar una ficha entera al backlog como un árbol Épica→Feature→Historia, estimar puntos, tomar una tarea (asignar + estado) sin pisar a otro, y comentar tarjetas — todo por lenguaje natural, y lo que escribe en el tablero, siempre con tu confirmación.

Cómo entra al repositorio Es herramienta/código → sube por rama feat/* + Merge Request a main. Los archivos propios de cada PC (la conexión de Azure, los secretos) no se versionan.

4.La conexión con Azure

El canal es el MCP (Model Context Protocol: el protocolo estándar que conecta un asistente de IA con una herramienta externa). Se usa el servidor @tiberriver256/mcp-server-azure-devops con npx -y (ejecuta el paquete de Node sin instalarlo). Se registra con un comando o con un archivo .mcp.json. Las reglas de redacción (AGENTS.md) siguen valiendo enteras: el MCP es solo el transporte.

Variables de entorno

VariableValorPara qué
AZURE_DEVOPS_ORG_URLhttps://dev.azure.com/<org>La organización de Azure
AZURE_DEVOPS_AUTH_METHODpat | azure-cliAutenticación con token, o con tu cuenta (Azure CLI)
AZURE_DEVOPS_PAT${AZDO_PAT} (solo método pat)El token (PAT = Personal Access Token). Su valor vive en una variable de entorno, nunca en un archivo
No hace falta certificado La conexión es a Azure DevOps en la nube (dev.azure.com), con certificado público válido: alcanza con esas variables. Solo si tu red corporativa intercepta el tráfico seguro se agrega NODE_EXTRA_CA_CERTS; en el caso normal no se usa.

Barreras al escribir (4, no negociables) Antes de crear/editar, el asistente verifica: (1) Tablero autorizado — solo se escribe en {{AZURE_ORG}} · {{AZURE_PROYECTO}} · {{AZURE_TEAM}}; cualquier otro se rechaza (el PAT ve toda la organización — incluye otros proyectos de la organización — por eso el guard vive en el skill, no en el token). (2) Deduplicación — busca en todo el tablero (no solo una Épica) por tag / título-objetivo / documento fuente si ya existe algo equivalente; si existe, no duplica: avisa con el link y propone reutilizar/relacionar. (3) Confirmación — propone y crea en turnos distintos; nada se escribe sin tu "sí" sobre lo ya mostrado. (4) Nivel + cardinalidad — por default llega hasta Historia (las Tareas técnicas solo en contexto dev/planning explícito) y la cantidad de Épicas/Features/Historias sale 1:1 del bloque enumerado de la ficha, nunca a criterio del modelo (detalle: §7 «Regla de cardinalidad»). Fuente: conocimiento/tablero-autorizado.md, conocimiento/deduplicacion-antes-de-crear.md, AGENTS.md.
Un tag, muchas Épicas posibles El tag temático (p. ej. reserva-salas) es un único string, siempre igual — pero no identifica el slice: un mismo tema puede tocar más de una Épica (más de un vertical slice). Por eso la deduplicación busca el tag en todo el board, no dentro de una sola Épica.

El hook anti-drift (.githooks/pre-commit)

Con tres copias (fuente + 2 espejos) existe el riesgo de que se editen y alguna quede vieja (drift). Se evaluó un pipeline de CI y se descartó — los runners los administra la organización — y en su lugar hay un hook de git versionado que corre solo en la máquina de quien edita skills, antes de cada commit, y verifica los dos espejos.

// Qué verifica el hook, para CADA espejo, antes de dejar commitear 1) Existe el espejo? (si se borro .agents/skills/ o .claude/skills/ entero, BLOQUEA) 2) Espejo == fuente en lo que entra al commit? (con eol=lf de .gitattributes -> misma verificacion en Windows/Linux/mac) 3) Lo que hay en disco quedo STAGED? (evita "sincronice el espejo pero me olvide el git add") -> si algo falla en CUALQUIER espejo: BLOQUEA el commit y dice que correr (bin/sync-skills.*)
Cómo se activaDetalle
Una vez por devgit config core.hooksPath .githooks
¿Quién lo necesita?Solo quien edita skills. Quien solo clona/usa no necesita nada: los hooks no vienen activados en el clone (por seguridad de git), por eso el paso es manual y por-dev.
Límite conocidoEs client-side: se puede saltear con git commit --no-verify. Es un guardarraíl, no una imposición dura — eso requeriría infra de servidor, descartada a propósito.
Un solo comando para ponerse al día bin/actualizar.sh (o .ps1 en Windows) hace git pull + activa el hook (core.hooksPath) + verifica que los dos espejos estén sincronizados, en un solo paso. Para regenerarlos tras editar una skill: bin/sync-skills.sh / .ps1 (herramienta del mantenedor, no del que solo usa el repo).

7.Backlog por vertical slice, estimación e historial

Estructura del backlog: monolito modular por vertical slices

La arquitectura del módulo es un monolito modular por vertical slices, y el backlog se arma para reflejarla. Por qué: en un monolito en capas todos los dominios comparten una capa de Service y una de Repository, así que dos tickets en paralelo (p. ej. de dos slices distintos) terminan editando el mismo archivo → conflictos de fusión. En un monolito por vertical slices cada dominio es un paquete propio con sus 4 capas internas (api · application · domain · infra); dos tickets de slices distintos editan archivos distintos → sin conflicto, aun desarrollándose al mismo tiempo. Un slice no importa clases internas de otro (solo su api pública); únicamente el slice de integración toca la conexión con el sistema externo.

Por eso cada ticket vive en UN slice y el backlog mapea Épica = slice/dominio:

Épica: Gestión de salas ← vertical slice (dominio); sin tag └─ Feature: Cancelación de reservas periódicas [tag: reserva-salas] └─ Historia: Cancelar una reserva periódica [RN-MOD-001] [tag: reserva-salas] ├─ Tarea (capa: domain) test de invariante RN-MOD-001 (TDD) [tag: reserva-salas] ├─ Tarea (capa: api) endpoint de cancelación [tag: reserva-salas] └─ Tarea (capa: infra) persistir el cambio [tag: reserva-salas] Épica: <slice-2> · Épica: <slice-n> · Épica: Integración-<sistema-externo> ← los otros slices

Tarea
(dev/planning)		Desglose técnico dentro del slice (capa api/application/domain/infra), con SDD + test de invariante (TDD) + indicador «requiere test de integración». No es parte del flujo funcional: por default se baja hasta Historia; las Tareas las crea Desarrollo en un segundo momento (planning).
El payoff Cada ticket queda acotado a un slice: el orquestador + los 3 sub-agentes (desarrollo, base de datos, testing) trabajan dentro de ese límite y entregan sin pisar otros tickets → paralelismo real. Hay un solo tag temático (p. ej. reserva-salas) que baja idéntico a toda la descendencia; el slice no lleva tag (es la Épica) y se filtra por su Épica.

Regla de cardinalidad — el conteo lo fija la ficha, no el modelo

El problema que resuelve: antes, pedir "bajá esta ficha" podía dar árboles de tamaño distinto según la herramienta (Claude/opencode/Antigravity) — más o menos Épicas/Features/Historias — porque las reglas fijaban el tipo de cada nodo (slice→Épica, flujo→Historia) pero no cuántos había, y hasta dejaban la granularidad como pregunta abierta ("¿una Historia por flujo o por pantalla?"). Ahora el conteo sale 1:1 de un bloque que la ficha declara.

## Derivación a backlog (lo cierra la curación + validación humana) ### Slices [Épicas] - [S-01] <slice/dominio> ### Capacidades [Features] - [C-01] <capacidad> · Slice: S-01 ### Flujos [Historias] - [F-01] <flujo> · Capacidad: C-01 - [F-02] <flujo> · Capacidad: C-01

1 Épica por cada [S-nn] (default 1; nunca se infieren slices no listados) · 1 Feature por cada [C-nn] · 1 Historia por cada [F-nn] — el flujo listado, nunca la pantalla — · 0 Tareas por default. Ningún nodo fuera de la enumeración; no se parte ni se fusiona un flujo por criterio propio. Si la ficha no trae el bloque (o tiene ⚠), no se deriva: se frena y se pide cerrarlo en el Cerebro — no se "cuenta a ojo" sobre la prosa.

Ejemplo gold Ficha con 1 slice + 1 capacidad + 2 flujos declarados → se crean exactamente 4 work items: 1 Épica + 1 Feature + 2 Historias. Mismo input, mismo árbol, en cualquier LLM — porque el modelo copia una estructura ya cerrada por un humano, no la inventa. Fuente: AGENTS.md §«Redacción y carga de tickets en Azure DevOps», conocimiento/organizacion-y-trazabilidad.md §5.

Estimación — por tokens + complejidad (la desarrolla la IA)

Como el desarrollo lo hace la IA, el puntaje no sale de un Planning Poker ni de un consenso humano: lo calcula la IA a partir de la complejidad a nivel sistema (capas, integraciones, reglas) y el consumo de tokens para resolver el desarrollo e investigar lo relacionado. Se expresa en escala Fibonacci (1, 2, 3, 5, 8, 13, 20; 13+ ⇒ partir) solo por compatibilidad con el campo Puntos de historia de Azure. La IA propone el número; el humano puede ajustarlo. Antes de codear estima con proxies (complejidad, integraciones, relacionadas); con el token real, ajusta y calibra. Detalle: skill estimar-story-points.

Historial — log resumido e indexable

El historial es un log liviano: una fila por ticket en historial/INDICE.md con tema (etiqueta), referencia (#ID de Azure + ruta del documento del Cerebro) y un resumen de una línea. No copia contenido y no escribe en el Cerebro Digital (solo lo referencia). Así, aunque se generen miles de tickets, sigue siendo una tabla indexable, no miles de archivos. El registro .md detallado (con ANTES/DESPUÉS) se crea solo para los que se marcan gold — los pocos que valen como modelo de estilo a imitar.

Por qué así Crear un archivo completo por ticket infla la memoria y se desincroniza cuando cambia el documento. Una fila por ticket tiene costo constante, se busca con Ctrl+F, y el detalle vivo queda donde corresponde: el ticket en Azure, el dominio en el Cerebro.

Trazabilidad — enlazar, no copiar

  • Un solo tag temático — techo duro sin prefijo, igual siempre, en cada nodo del árbol — no solo la Épica. El slice no lleva tag (ya es la Épica); nunca el nombre del producto/repo como tag (no filtra nada, lo comparte todo el tablero).
  • Relaciones Parent (jerarquía) y Related (mismo tema); los #ID son dato duro (⚠ hasta confirmarlos).
  • Documento fuente como ruta al .md — referencia, nunca el contenido copiado.
  • Reglas de negocio [RN-…] en la Descripción, citadas en cada criterio Gherkin.
  • Traza en las dos direcciones: ficha ↔ ticket ↔ fila del historial, por ruta + #ID.

Cambios y desfase (drift)

Cuando un documento cambia y la tarjeta ya existe: consultar-backlog (solo lectura) detecta el desfase; sincronizar-backlog propone el DIFF antes de pisar y, al aplicar, dispara el aviso (comentario con @mención, que la persona responde cuando lo leyó, + un query guardado "Mis items que cambiaron", el "git pull" del backlog). Lo ya entregado no se reabre: la modificación nace como un Bug (si se desvió del contrato) o una Historia nueva (si cambió la regla). Detalle: conocimiento/cambios-en-el-backlog.md.

8.Glosario

work item
Cada tarjeta del tablero de Azure DevOps: Épica, Feature, Historia de usuario, Tarea o Bug.
Cerebro Digital
La documentación del proyecto en fichas .md: la fuente única del dominio (cerebro-digital/).
MCP (Model Context Protocol)
El protocolo estándar que conecta un asistente de IA con una herramienta externa; acá, con Azure DevOps.
PAT (Personal Access Token)
Un token de acceso personal: funciona como una contraseña para que una app entre a Azure en tu nombre.
Azure CLI
La herramienta de línea de comandos de Azure; permite autenticarte con tu cuenta (az login) sin manejar un token.
Gherkin
La forma de escribir criterios verificables con Dado / Cuando / Entonces (siempre en español).
Fibonacci
La escala de puntos 1, 2, 3, 5, 8, 13, 20; de 13 en adelante conviene partir la historia.
gold
Un ticket marcado como buen modelo a imitar; es el único caso en que se guarda su registro detallado.
espejo de skills
Copia versionada de las skills, idéntica a la fuente configuracion-ia/skills/. Hay dos: .agents/skills/ (Antigravity/opencode) y .claude/skills/ (Claude Code) — cada herramienta busca skills en una ruta fija propia.
hook pre-commit
Un script de git (.githooks/pre-commit) que corre antes de cada commit; acá bloquea si alguno de los dos espejos de skills quedó desincronizado. Se activa una vez por dev.
bloque de derivación a backlog
La sección ## Derivación a backlog de una ficha: enumera sus Slices/Capacidades/Flujos y fija, 1:1, cuántos work items se crean al derivarla.
datos personales sensibles protegidos
Datos personales sensibles reales de una persona (nombre, identificador, dato sensible…). Prohibidos en tickets y fichas: se reemplazan por marcadores como <persona>.
reglas de negocio [RN-…]
Las reglas del dominio, numeradas (p. ej. [RN-MOD-02]), para citarlas desde los criterios.
backlog
La lista de trabajo del equipo en el tablero.
Merge Request
El pedido para incorporar los cambios de una rama a main, con revisión previa (en GitLab).
